## 1. Executive Overview

This repository implements a full multi-robot mining navigation stack using centralized-training MADDPG with three physically simulated robots in a PyBullet mining arena.
All statements in this document are grounded in the current `train_maddpg_v3.py`, `environment_maddpg_v3.py`, and the top-level project documentation files you attached. [file:25][file:26][file:28][file:27][file:31]

The core idea is: **define a strict 90% mastery curriculum over realistic mining geometry, then engineer the reward, replay buffer, and rollout system so that the team-policy can actually reach that bar without reward hacking.** [file:25][file:26][file:30]

### 2.2 Algorithmic Core: MADDPG V3

The final trainer implements a CTDE MADDPG variant with: [file:25]

- Shared **Actor**: 3-layer MLP with hidden dimension 384, final `Tanh` output, and small-range initialization on the last linear layer to avoid initial action saturation.
- Shared **TwinCritic**: twin Q-networks (`q1`, `q2`) with 3 hidden layers (384) and output clamped to [−100, 100] for numerical stability.
- **Twin critic minimization** for target Q: `min(q1', q2')` as in TD3-style critics.
- **Target networks** for both actor and critic with soft update (`tau=0.005`).
- **Policy smoothing**: Gaussian noise on target actions, clipped and then `Tanh`-clamped to [−1, 1].
- **Gradient clipping** on both actor and critic (max-norm 1.0) during updates.
- Optional `torch.compile` for models when using CUDA to reduce Python overhead. [file:25]

All three agents are instances of the same `MADDPGAgent` class with shared architecture; they differ only by agent index and observation stream. [file:25]

### 2.3 Environment Core: MiningEnvironmentMADDPG_V3

The V3 environment keeps the core geometry and physics from V2, but explicitly defines: [file:26][file:28]

- **Static mining obstacles** from SDF:
  - 28 pillars (x, y, radius), 3.0m height.
  - 10 ore piles as box-like structures (x, y, size_x, size_y, size_z, yaw).
  - 6 equipment pieces (x, y, size_x, size_y, size_z, yaw).
- **Robots**:
  - Differential-drive robots with radius `robot_radius`, wheel radius and chassis height taken from the mining robot spec. [file:28]
  - Frozen-on-goal semantics: when a robot reaches its goal threshold, it is marked `frozen` and its velocity is reset to zero.
- **Collision detection**:
  - Robot–obstacle collisions: check circle overlap `(rx - ox)^2 + (ry - oy)^2 < (r_robot + r_obstacle + 0.05)^2` per robot. [file:26]
  - Robot–robot collisions: pairwise distance check `(x1 - x2)^2 + (y1 - y2)^2 < (2*robot_radius + 0.05)^2`; if violated, both robots are marked as colliding. [file:26]
- **LiDAR**: identical to V2 implementation, using 360-degree ray casting with vectorized checks against obstacles. [file:26][file:30]
- **Spawn logic**:
  - Robots are spawned on an 8.0m radius ring around the origin with random global angle and small per-robot jitter. [file:26]
  - Each robot gets an independently sampled goal generated by `_generate_valid_goal(spawn_x, spawn_y)`, using the V2/V3 curriculum distance ranges.

The environment tracks per-robot state including position, velocity, distance to goal, collision counts, and `frozen` flags, which are used for reward computation and success statistics. [file:26]

## 3. Curriculum Design and Phase Gating

### 3.1 V2 vs V3 Curricula

Two curriculum definitions exist in the code: [file:25][file:26]

- **V2 original** (`CURRICULUM_V2_ORIGINAL`, 9 phases):
  - Easy1, Easy2, Easy3, Med1, Med2a, Med2b, Hard1, Hard2, VHard.
  - Heterogeneous thresholds and step limits per phase (e.g. Med2a/b ranges 4–6m, varying steps). [file:26]
- **V3 smooth** (`CURRICULUM_V3_SMOOTH`, 8 phases):
  - Easy1, Easy2, Easy3, Med1, Med2, Hard1, Hard2, VHard. [file:26]
  - Unified **0.75m goal threshold** across all phases.
  - Monotonically increasing spawn distance ranges and episode length:
    - Easy1/Easy2/Easy3: shorter ranges, lower max_episode_steps.
    - Med1/Med2: larger spawn ranges & moderate steps.
    - Hard1/Hard2/VHard: long cross-arena distances with higher step caps.

The trainer selects tables based on CLI flags: [file:25]

- `--curriculum-mode v2_original` → `PHASE_LIST_V2`, `PHASE_CONFIG_V2`, `PHASE_NOISE_V2`, `PHASE_GROUPS_V2`.
- `--curriculum-mode v3_smooth` → `PHASE_LIST_V3`, `PHASE_CONFIG_V3`, `PHASE_NOISE_V3`, `PHASE_GROUPS_V3`.

### 3.2 90% Mastery Gate (Per Phase)

Both V2 and V3 share the same **advancement logic** in `train_maddpg_v3.py`: [file:25][file:30]

- For each phase `phase_name`, advancement requires:
  - `phase_episode_count[phase_name] >= phase_config[phase_name]["min"]`.
  - A rolling mastery window (default 500 episodes) of **individual success fraction** ≥ 90%.
  - The same rolling window of **team success** ≥ 90%.
- There is **no episode cap** (`max_episodes` is effectively 999999): phases are **mastery-only**, not time-based.

The `PHASE_CONFIG_V3` table is: [file:25]

- Easy1: `min=300`, `threshold=0.90`.
- Easy2: `min=400`, `threshold=0.90`.
- Easy3: `min=500`, `threshold=0.90`.
- Med1: `min=600`, `threshold=0.90`.
- Med2: `min=800`, `threshold=0.90`.
- Hard1: `min=1000`, `threshold=0.90`.
- Hard2: `min=1500`, `threshold=0.90`.
- VHard: `min=2000`, `threshold=0.90`.

Every 500 episodes, the trainer computes per-phase rolling mastery using a deque of recent success values and checks whether the current phase meets the gate; only then does it advance and broadcast `set_phase` to all workers. [file:25][file:31]

### 3.3 Phase-Grouped Replay and Noise

The curriculum is coupled to replay sampling and exploration noise: [file:25]

- **Phase groups** for replay sampling (`PHASE_GROUPS_V3`):
  - Easy1/Easy2/Easy3 share a group.
  - Med1 and Med2 share a group.
  - Hard1/Hard2/VHard share a group.
- When sampling batches, the replay buffer:
  - Draws ~30% of the batch from the success pool.
  - Within each pool (main/success), prioritizes transitions whose `_phase` belongs to the phase group of the current phase.

**Noise schedules**: `PHASE_NOISE_V3` defines base exploration noise per phase, e.g.: [file:25]

- Easy1/Easy2/Easy3: 0.20, 0.18, 0.16.
- Med1: 0.13.
- Med2: 0.10.
- Hard1/Hard2/VHard: 0.08, 0.06, 0.05.

The actual noise is computed in `compute_adaptive_noise`, which:

- Raises noise during early phase episodes (`phase_episode_count < 100`).
- Reduces noise when rolling 100-episode **team** success ≥ 90%.
- Increases noise again when the phase is stuck at low team success (< 30% for 2000+ episodes).
- Uses the variance of the last 400 successes to boost exploration when stuck in a plateau (50–84% region) with low variance. [file:25]

This couples curriculum (phase), exploration, and replay groups in a consistent way.

## 4. Reward Design in V3 (Reward+Smooth Mode)

### 4.1 Reward Mode Selection

`train_maddpg_v3.py` supports different reward-configurations via `--reward-mode`: [file:25]

- `v2_baseline` – dense, original V2 reward with multiple shaping terms.
- `v3_clean` or similar – pruned/clean reward variants (in earlier iterations).

The **canonical V3 run** is documented at the top of `train_maddpg_v3.py` as: [file:25]

> Canonical mode: `--reward-mode v2_baseline --curriculum-mode v3_smooth`
> - V3 smooth curriculum (8 phases, unified 0.75m threshold)
> - Goal-first reward hierarchy with sparse shaping
> - 90% mastery (ind + team), no episode cap
> - 40% of catastrophe episodes kept in replay buffer
> - One-goal and zero-goal timeout penalties injected into terminal reward
> - Live Med1 gate metrics logged every 500 episodes

### 4.2 Event Structure and Reward Terms

In the V3 environment, the high-level reward hierarchy is: [file:26]

- **Per-robot goal completion**: largest per-robot positive event; robot is marked `frozen`.
- **Partial team completion**: bonus when at least `N-1` robots are frozen.
- **Full team completion**: largest shared team bonus when all robots are frozen.
- **Collision penalty**: per-step penalty when a robot is in collision, via `collision_count` and collision flags.
- **Timeout penalties**: applied by the trainer on terminal transitions when episodes end via truncation:
  - `partial_timeout_penalty` when some but not all robots are frozen.
  - `zero_timeout_penalty` when no robot reaches its goal.

The environment returns per-robot reward dictionaries; the trainer then applies terminal shaping for timeouts before pushing into the replay buffer. [file:25][file:26]

### 4.3 Timeout Penalties in the Trainer

`train_maddpg_v3.py` exposes two CLI parameters for timeouts: [file:25]

- `partial_timeout_penalty` (default 10.0).
- `zero_timeout_penalty` (default 6.0).

When building `episode_data` and transitions, the trainer checks the episode end reason and injects these penalties into the terminal rewards for:

- Episodes ending by **timeout** with exactly one or `N-1` robots reaching the goal (partial success).
- Episodes ending by timeout with **zero goals**.

This is specifically designed to prevent the one-goal timeout basin observed in older runs, where partial timeouts had relatively high return but did not count toward the 90% **team** success gate. [file:25][file:22]

### 4.4 Catastrophe Handling (Collision-Heavy Episodes)

The trainer classifies episodes with **100 or more collisions** as catastrophe episodes. In V3: [file:25]

- Approximately 40% of these catastrophe episodes are **kept** in replay (`success_pool_ratio` and catastrophe retention logic), the rest are discarded.
- Catastrophic episodes carry heavy negative reward through repeated collision penalties and, often, failure to reach goals.

This is a deliberate compromise between:

- Exposing the critic to enough catastrophic transitions to learn to avoid them.
- Avoiding complete domination of the replay buffer by rare but extremely negative episodes.

## 5. Replay Buffer and Sampling Logic

### 5.1 Data Structures

The V3 replay buffer is explicitly engineered for both performance and phase-aware sampling: [file:25]

- Two list-backed circular buffers:
  - `_main_buf` for general transitions.
  - `_succ_buf` for success-biased transitions.
- Each has a fixed capacity (total default 200,000 transitions; success pool ~20%).
- Per-buffer **phase index**: dictionaries mapping `phase_name → set(indices)` for O(1) lookup of indices belonging to specific phase groups.

Unlike simple `deque`-based buffers, this supports:

- O(1) push with phase indexing.
- O(|phase_group|) sampling for phase-consistent batches without scanning the entire buffer.

### 5.2 Sampling Policy

`ReplayBuffer.sample(batch_size, current_phase)` performs: [file:25]

1. Determine phase group: `same_phases = PHASE_GROUPS_Vx[current_phase]`.
2. Compute `n_success = min(int(batch_size * 0.3), len(_succ_buf))`.
   - If `success_phase_filter` is enabled and there are enough entries in the same phase group, preferentially sample those indices.
3. Compute `n_main = batch_size - n_success`.
   - Half of `n_main` attempts to be phase-consistent (`same_idx`), half uniformly sampled from `_main_buf`.

This ensures:

- ~30% of each batch is drawn from success experiences (possibly phase-filtered).
- Another ~35% is same-phase failures.
- Remaining ~35% comes from the global experience pool.

Crucially, this stabilizes training in hard phases (Med1+) by ensuring that:

- Success signals are present in every gradient step, even when raw environment success rates are low.
- Phase mixing across Easy/Med/Hard is controlled, preventing Easy successes from flooding Hard-phase learning.

### 5.3 Success Buffer Refresh

The buffer exposes `refresh_success_buffer(keep_ratio=0.5)`, which:

- Keeps only the most recent `keep_ratio` of success transitions in `_succ_buf`.
- Rebuilds the phase index for that reduced set.

This acts as a time-based decay for success experiences, preventing very old (easier phase) successes from dominating success sampling once the system has moved into harder phases. [file:25]

## 6. Parallel Environment Rollout

### 6.1 Architecture

The parallel rollout infrastructure is documented in `PARALLEL_ROLLOUT_DOCUMENTATION.md`: [file:31]

- Main process handles all neural network forward/backward passes and replay buffer updates.
- N worker processes each host an independent PyBullet environment (`MiningEnvironmentMADDPG_V3`).
- Communication is via pipes with a simple command protocol:
  - `('reset',)`, `('step', actions)`, `('get_attr', name)`, `('set_attr', name, value)`, `('call_method', name, args, kwargs)`, `('close',)`.

This follows the SubprocVecEnv pattern used in OpenAI Baselines/Stable-Baselines3, but is tailored to this environment and curriculum. [file:31]

### 6.2 CPU Budgeting

`train_maddpg_v3.py` computes a **CPU budget** at startup: [file:25][file:31]

- `n_cpus = os.cpu_count()`.
- If `--torch-threads` is not specified:
  - `torch_threads = max(1, n_cpus - num_parallel_envs)`.
- Enforces `env_workers + torch_threads <= cpu_count` where possible, printing a warning otherwise.

This prevents severe CPU oversubscription when running with many parallel environments.

### 6.3 Modes and Launch Scripts

`PARALLEL_ROLLOUT_DOCUMENTATION.md` describes:

- **Single-env mode** (original behavior): [file:31]
  - `python3 train_maddpg_v3.py --episodes 100000 --reward-mode v2_baseline --curriculum-mode v3_smooth`.
- **Parallel rollout**:
  - `--num-parallel-envs N` selects N worker processes.
  - `run_single_max.sh` configures a single high-throughput job.
  - `run_parallel.sh` configures dual-pane comparison jobs sharing CPU budget.

Episodes are collected in parallel, and batches of complete episodes are then used for MADDPG updates in the main process. [file:31]
